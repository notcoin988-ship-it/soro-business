# Прод-деплой: сервер, HTTPS, бэкапы

> **Этот файл описывает, как поднять СТЕНД на сервере с доменом и HTTPS.
> Это не значит «можно пускать клиентов банка».** Что мешает боевому
> запуску — в конце файла, раздел «Чего не хватает для продакшна». Список
> короткий, но каждый пункт блокирующий.

Что нужно от сервера: 4 ядра, 16 ГБ памяти, 60 ГБ диска, Docker 24+,
открытые 80 и 443. Меньше памяти — TEI не прогреется: замер на машине с
15,4 ГБ лежит в комментарии к `docker-compose.override.yml`.

## 1. Первый запуск

```bash
git clone <репозиторий> && cd soro-business
cp .env.example .env          # секреты — у тимлида
export SORO_DOMAIN=soro.example.tj      # домен уже смотрит A-записью на сервер
cd console && npm ci && npm run build && cd ..   # консоль соберётся в console/dist

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
docker compose exec backend alembic upgrade head
```

`docker-compose.override.yml` на сервере **не нужен** — он локальный, для
машины разработчика. Compose подхватывает его автоматически, поэтому на
проде его либо удаляют, либо переименовывают.

Проверка:

```bash
curl https://$SORO_DOMAIN/health          # {"status":"ok", ...}
curl https://$SORO_DOMAIN/console/        # консоль
```

## 2. Что делает Caddy

Сертификат Let's Encrypt получает и продлевает сам — ни certbot, ни крона.
Конфиг в `deploy/Caddyfile`, три вещи в нём не косметические:

* **`flush_interval -1` для `/widget/stream` и `/api/playground/stream`.**
  Без него ответ бота приходит одним куском в конце: буферизация ломает
  SSE, и «печатается по мере генерации» превращается в шесть секунд
  молчания.
* **`X-Frame-Options` НЕ ставится.** Виджет живёт в iframe на сайте банка;
  запрет фреймов сломал бы ровно то, что мы продаём.
* **Домен из окружения.** Нет домена — `SORO_DOMAIN=:80`, Caddy работает
  без TLS: сертификат на IP-адрес не выдают.

Порты бэкенда и базы наружу не публикуются: до них ходит только Caddy
внутри сети compose. На стенде разработки 5432 и 8000 открыты — там это
нормально, здесь недопустимо.

## 3. Бэкапы

Контейнер `backup` снимает `pg_dump -Fc` раз в сутки в volume `backups`,
хранит 14 дней (`BACKUP_KEEP_DAYS`). Формат custom, а не SQL: он сжат,
восстанавливается выборочно и переживает pgvector — обычный дамп требует,
чтобы расширение уже стояло.

```bash
# снять снимок прямо сейчас
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
    exec backup /bin/sh /backup.sh

# посмотреть, что есть
docker compose ... exec backup ls -lh /backups

# восстановить (ПЕРЕЗАПИШЕТ данные)
docker compose ... exec -T db pg_restore -U soro -d soro --clean --if-exists \
    < soro-2026-08-13-0300.dump
```

**Проверять восстановление, а не наличие файлов.** Бэкап, который никогда
не разворачивали, — это не бэкап. Раз в месяц: поднять пустую базу,
залить в неё последний дамп, открыть консоль и убедиться, что документы и
диалоги на месте.

Дампы лежат в docker volume, то есть на том же диске, что и база. Для
пилота этого мало: настроить выгрузку в S3 или на второй сервер — задача,
которую надо закрыть до боевого запуска, и она не решается этим файлом.

## 4. Нагрузочный прогон

```bash
docker compose ... exec backend python scripts/loadtest.py --users 25
```

Гоняет полный путь клиента через виджет: POST, ожидание ответа в
SSE-потоке, разбор `final`. Замер на демо-стенде (4 ядра, CPU, заглушка
модели):

| одновременных клиентов | медиана | 95-й перцентиль |
|---|---|---|
| 1 | 5,2 с | — |
| 8 | 10,5 с | 10,5 с |
| 25 | 16,0 с | 22,2 с |

Сбоев ни в одном заходе не было — все клиенты дождались ответа. Но время
растёт линейно, и причина известна: **эмбеддинги считаются на CPU по
3–4 секунды и по очереди**, TEI обрабатывает батчи последовательно. Это
дно, ниже которого не опуститься никакой параллельностью на этом железе.

Что с этим делать перед пилотом — по убыванию эффекта:

1. GPU для TEI: тот же образ с тегом `cuda`, поиск ускоряется примерно в
   двадцать раз, и всё остальное перестаёт быть узким местом;
2. кеш эмбеддингов частых вопросов: на демо половина вопросов повторяется;
3. второй воркер uvicorn НЕ поможет и сейчас запрещён: SSE-шина и хаб
   сокетов живут в памяти процесса (см. пункт 5 ниже).

Норматив «ответ < 6 секунд» из раздела 3 относится к одиночному вопросу на
незагруженном стенде и этими цифрами не отменяется — но обещать его при
двадцати пяти одновременных клиентах на CPU нельзя.

## 5. Что проверить перед показом банку

- [ ] `curl https://$SORO_DOMAIN/health` отвечает по HTTPS, сертификат
      валидный;
- [ ] экран 01 — в чек-листе готовности нет галочек напротив
      неподключённых каналов;
- [ ] экран 05 — Telegram «Активен», вебхук смотрит на боевой домен, а не
      на старый ngrok;
- [ ] `docker compose ... exec backup ls /backups` — есть хотя бы один
      снимок;
- [ ] `scripts/acceptance.py` проходит все автоматические шаги.

## 6. Чего не хватает для продакшна

Стенд по этому файлу поднимается на домене с HTTPS и годится для демо и
пилота под присмотром. Порядок — по опасности; помечено, что закрыто, а
что нет.

ОСТАЛОСЬ ДВА БЛОКЕРА: вход в консоль (пункт 1) и WhatsApp (пункт 9).
Первый — единственный, который мешает пускать на стенд клиентов банка.

**1. Консоль открыта всем, у кого есть адрес.** Входа нет: `api/auth.py`
— заглушка, форму пароля убрали как декоративную. На публичном домене это
открытая админка: любой видит переписку клиентов с настоящими номерами
карт и паспортов, может отвечать от имени банка, закрывать диалоги и
заводить банки. Нужен настоящий вход (раздел 9 ТЗ) плюс роли: оператор не
должен уметь то, что умеет админ.

**2. Лимиты на виджете — закрыто.** 20 сообщений в минуту на клиента,
вопрос обрезается по 1000 символов, выдача токена склейки — 5 в минуту.
Счётчик в Redis, поэтому лимит общий на все воркеры, а не умножается на
их число. Что осталось: капча на первое сообщение для публичного сайта —
это решение банка, а не наше.

**3. Лимит загрузки — закрыто.** 25 МБ, файл пишется кусками по
мегабайту: `await file.read()` целиком держал его в памяти, и
полугигабайтный «скан архива» клал бы процесс раньше, чем кончился диск.

**4. Секреты — закрыто наполовину.** Любой секрет теперь можно задать
файлом: `SORO_API_KEY_FILE=/run/secrets/soro`. Так работают docker secrets
и почти все хранилища, и значение из файла перевешивает переменную. Сам
`.env` на стенде остаётся — это решение того, кто разворачивает прод.

**5. Масштабирование — закрыто.** События между процессами ходят через
Redis pub/sub (`core/bus`), в проде стоит `--workers 2`. Проверено на
стенде: оба воркера подписаны на каналы, клиенты получают ответы
независимо от того, какой процесс их считал. Дальше упирается уже не в
это, а в TEI (пункт 6).

**6. Производительность — частично.** Повторяющиеся вопросы больше не
считаются заново: вектор кешируется в Redis на сутки, замер на стенде —
356 мс против 12 мс. На демо половина вопросов повторяется, и это
заметно. Но 25 одновременных клиентов с РАЗНЫМИ вопросами по-прежнему
упираются в TEI на CPU — тут нужен GPU, и это железо, а не код.

**7. Бэкапы — закрыто.** `BACKUP_MIRROR_DIR` копирует дамп во второй
каталог (сетевой шар, внешний диск, папка синхронизации). Репетиция
восстановления — `scripts/restore_check.sh`: разворачивает последний дамп
во ВРЕМЕННУЮ базу и сверяет, что таблицы на месте. Проверено: 2
воркспейса, 110 документов, 500 фрагментов, 132 сообщения.

**8. Мониторинг — закрыто.** `GET /health/ready` проверяет базу, Redis,
эмбеддинги, модель и вебхук Telegram по отдельности. `scripts/watchdog.py`
спрашивает его раз в минуту и пишет в Telegram на ПЕРЕХОДЕ состояния —
лежащий ночью стенд не выдаст к утру триста одинаковых сообщений.

**9. WhatsApp не реализован**, хотя заявлен в ТЗ и виден на экране 05.

**10. Хранение — закрыто наполовину.** Аудит-лог чистится по
`AUDIT_KEEP_DAYS` (по умолчанию 1095 — те самые три года из ТЗ), чистка
идёт в том же суточном цикле, что и бэкап. Переписка клиентов хранится в
открытом виде — так и надо для оператора, — но политику доступа и сроки
должна утвердить служба безопасности банка.
